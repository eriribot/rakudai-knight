【Rakudai · MVU Output Format / G04 / T01】
Read the current branch state and follow [MVU]变量更新规则. Main and secondary APIs use the same business-field permissions; code manages identity metadata, derived stages and settlement receipts.
End the narrative with exactly one <UpdateVariable> containing <Analysis> then <JSONPatch>, with all closing tags. Analysis is concise English: check scene, each growth target, affection and support separately, contact/profile facts and tournament changes. State old→final values or concrete no-change reasons; no major event is not a reason to skip everyday changes.
JSONPatch is one complete JSON array. No fences, headings, comments, ellipses or escaped tags. Do not impose a word or operation limit that omits valid updates. Analysis alone does not save data.

【Operations and Types】
Paths start with /玩家, /场景 or /人际, never /stat_data. Use add for missing entries/parents, replace for existing values, remove for confirmed erroneous dynamic entries. Submit final values, not increments. Prefer changed child fields; when supplying an object, preserve unrelated existing data. Do not reset /系统, /玩家/性别, /玩家/综合初评, growth receipts or terminal roster visibility through parent replacements.
Strings, null, {}, [], numbers and native true/false have different meanings. Names are stable non-empty keys without /, ~, __proto__, prototype or constructor. Framework $internal/display_data/delta_data are not business fields.

【Player and Abilities】
/玩家/魔人觉醒 is native true/false only. No parallel realm flag; a confirmed awakening itself gives no experience. Main and secondary APIs may correct confirmed player data, /玩家/六维, /玩家/登记等级 and /玩家/成长/经验 final values.
六维 keys: 攻击力, 防御力, 魔力量, 魔力控制, 体能, 运气. Grades: F,F+,E,E+,D,D+,C,C+,B,B+,A,A+,S; empty string means unconfirmed. 登记等级 uses F through A or null; it records actual registration, not automatic experience advancement.
/玩家/伐刀能力 contains 能力系别, 能力本质, 共通限制, 招式. 能力系别 is empty or 体能强化系/自然干涉系/概念干涉系/因果干涉系. 招式 and /玩家/其他能力 map stable names to {说明:string,条件与代价:string,掌握状态:待确认|学习中|已掌握}. Use confirmed learning results; descriptions and method names are free text.

【Growth】
Create missing /玩家/成长 and /玩家/成长/申请 parents with {} before children. Each request has 来源事件, 目标, 经验, 成果; 类型 and 方式 are optional free-text descriptions. 来源事件 exactly matches an actual /场景/已发生事件 key saved before the request in this patch. 成果 is non-empty actual result text.
目标 is 魔力控制, 体能 or 魔力量, or an array of these. 魔力量 growth requires 魔人觉醒:true. 经验 is a non-negative JSON integer or an equal-length array paired with target positions. A single number is the TOTAL across unique targets: [魔力控制,体能,魔力量] with 90 means 30 each. Divide evenly, assigning remainders in target order; duplicate targets use their first occurrence. An ineligible target does not donate its share to others.
Use stable request names; code derives stable per-target names for arrays. One source result and target earns once, up to 9999 per target across the entire real assistant reply. No fixed category/method enum, time conversion or separate breakthrough approval. Actual control and body training may both qualify in one event; judge participation from facts, not words such as “mental” or “simulation”.
New rewards use requests; explicit experience corrections use /玩家/成长/经验/<目标>. If both are submitted for a target, the final value wins and the request is receipted without a second addition. Experience is progress relative to the supplied current grade. Code repeatedly promotes while thresholds are met and preserves remainder, including old overflow with no new request. Do not write version/history/receipt fields or forge a new source to re-claim a result. Malformed requests remain pending locally; they do not invalidate other saved facts.

【Scene, Events and Schedule】
场景 fields: 当前卷 (integer 1—19), 当前章 (exact injected directory key), 阶段 (未开始|进行中|已结束), 时间, 地点, 切入说明 (strings). Follow actual completion markers. Main and secondary share one chapter advance per reply; do not finish the next chapter again during correction.
已发生事件 maps stable names to {卷号:integer,章段:string,结果:non-empty string,参与者:string[],知情者:string[]}. Record the chapter where it happened, not a future chapter. Existing event names stay stable.
日程 is optional and maps stable names to {类型:比赛|训练|约定|其他,日期:string,时间:string,地点:string,参与者:string[],状态:待定|已安排|进行中|已完成|已取消,说明:string}. 日期 is a real YYYY-MM-DD or empty. Plans and elapsed dates do not prove completion.

【People】
New /人际/<姓名> requires 关系:string,态度印象:string,好感:number|null,支援度:integer|null,羁绊阶段:未定|未建立|C|B|A|S,变化依据:string. Ordinary new no-change records start at 0/0 and 未建立; confirmed background may use its assessed final values. Existing values continue from their real baseline.
Optional fields: 性别 (未知|男性|女性), 联系状态 (仅识别|已建立联系), 联系依据:string, 已加联系方式:boolean, 已知资料:{身份?,登记等级?,灵装?,已知能力?} with string children. Contact interaction and exchanged contact details are independent. Never recreate names in /系统/已删除人物.
好感 is 0—1000; 支援度 is integer 0—320. Write justified final values and concise 变化依据. Ordinary friendliness, eased defenses and major trust changes are narrative guidance, not hard numeric tiers. No separate 好感突破依据 is required. Scores can be corrected up or down; each field remains independent. Code derives 羁绊阶段 and 恋爱阶段, which never invent actual relationship events. Do not write 名册隐藏.

【Tournament T01】
/场景/选拔赛 is optional; create {} first, then business entries. Defaults: 版本:T01,赛季:破军学园选拔赛,状态:未开始,总轮次:20,代表名额:6,号池规模:288,模式:跟随系统,名册:{},比赛:{}. Use current system protagonist mode; do not set a separate player mode.
名册/<ID>: {姓名:string,来源:正典|原创|玩家,参赛状态:参赛|退选|取消资格,初始战绩?:{截至轮次:integer,胜场:integer,败场:integer,积分?:integer,依据:non-empty string}}. Missing initial results mean unknown, not zero. Only confirmed unplayed records may start at zero with a factual basis.
比赛/<ID>: {轮次:integer,甲方:rosterID,乙方:rosterID,日期:string,时间:string,地点:string,状态:待定|已安排|已完成|已取消,胜者?:rosterID,弃权方?:rosterID,甲赛前胜场?:integer,乙赛前胜场?:integer,依据:string}. Completed matches require actual winner and basis. Optional unknown values are omitted, not fabricated. The same pair cannot play twice in a season; each person plays at most once per round. Do not overlap baseline-covered rounds with new match records.
Wins, points and rankings are derived from the ledger. Winner points = 10 + 10 × opponent's actual pre-match wins; loser gets 0. Never substitute round−1 for missing wins. Amend the same ID to correct a result; do not append a second scoring entry or write a preset original-story leaderboard.
