# 2026-10-29 剧情注入修复

交付方式：组件更新。玩家反馈截图中的预览能够读取世界书，但没有本次加载后的注入确认。本次在实际注入器源码的离线事件测试中复现了相同现象；尚未连接反馈玩家的酒馆，不能把截图当作唯一根因的证明。

## 可复现的问题

1. 酒馆提示词预览触发生成事件时，注入器先取消正式请求，再判断这是预览。预览若插入正式生成流程，会撤回剧情块；也会覆盖之前有用的成功或失败状态。
2. 请求中已有完整旧剧情块时，偶数助手楼层分支没有把清理结果写回原消息，新增剧情块后出现重复，发送前校验将其撤回。
3. 默认生成类型在前端事件中归一为 normal，末端却拿未归一的类型比较，空类型请求会被误撤回。本地已核对的普通发送按钮明确传 normal，这项属于兼容修复，不能据此断言玩家的普通发送原因。

预览现在直接跳过，不取消正式请求、不覆盖正式诊断；奇偶分支共同清理旧块，继续使用原有交替位置。后台静默生成、助手后台请求、继续与普通发送类型不匹配时仍被隔离。终端的空记录说明改为本次加载期间，避免把刷新后清空的内存记录解释为整个存档从未注入。

## 后续复核：修订 20261029.2

玩家反馈替换前一修订后仍显示旧句“预览、后台或非剧情生成：跳过注入”。已核对前一修订两个 JSON 均不含该句；终端直接显示当前注入器的 reason。因此仍需区分旧面板状态、另一脚本实例覆盖、实际导入内容不同等情况，不能仅靠截图认定是新的奇偶失败。

本轮重点对照奇偶改动前的 Git HEAD 与当前实现，复核了计数、MVU 来源、宿主流式时序、尾消息追加和撤回：

- 奇偶只决定位置，没有某一奇偶跳过的规则。实际玩家包在助手数 1、2、178、179、180 的普通发送中均确认成功，恰好一个剧情块；标准交替结构下来源 356 楼是第 179 条助手回复。
- 普通发送、续写、重生成、swipe 均能注入；续写使用当前助手状态，所以其位置可能与首次生成不同。这是现有计数语义，本轮没有更换策略。
- 固定 ST 源码在发送前检查完成后才创建流式助手楼层，没有原生“提前建空楼导致读错状态”的证据。
- 确认三项奇偶修改回归并修复：取消时整条删除新 user 而误丢其他监听器追加的文字；候选保存活动数组引用导致原地重排被误放行；宿主浅复制后再取消留下空 user。修前新增测试得到 17/20，仅这三项失败。

修订 20261029.2 恢复独立消息顺序快照，同时保留原数组供撤回；只有本注入器新建、且完全由完整剧情块组成的 user 消息才整条移除，其他文字和媒体保留，原本的空 user 不清理。实际运行修订号加入 getStatus.reason，因此已有终端点击“刷新注入预览”也应看到“注入器修订 20261029.2”，不依赖再替换终端。

若刷新后没有修订号或仍出现旧句，优先检查角色脚本与全局脚本中的重复注入器。若修订号正确仍漏注入，保留它后面的具体原因再定位。当前核查仍不能替代反馈玩家实际环境的发送请求证据。最新测试总数、源码与输出哈希以同目录 manifest 为准；上方 17/17 为前一修订的历史结果。
