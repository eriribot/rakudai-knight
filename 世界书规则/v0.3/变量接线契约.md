# v0.3 变量接线契约（开发资料，不注入正文）

目标：MVU 非同层卡。保留真实用户/助手消息与对应楼层、swipe 的状态分支；前端本机草稿不是当前聊天存档。

## 建档边界

页面 `readOpeningDraft()` 是表单、照片和已导入评定的唯一读入口。版本 3 的 profile 增加 `ability`、`limits`、`style`、`assessment`、派生 `rating`。具体 JSON 示例由页面导出，不手工维护另一套平行字段。

| 数据 | 当前所有者 | 未来接入 MVU 的边界 |
|---|---|---|
| 身份、能力说明、六维 | 玩家建档／AI 提议经用户显式应用 | 初始化事务一次写入当前聊天的玩家记录，不能写全局人物池 |
| rating.score、rating.base | 确定性脚本 | 脚本唯一写者，AI 不直接 Patch |
| assessment.reasons、adjustment、reviewReason | AI 提议经验证 | 验证合法档位、完整理由、±1 与绑定依据后接受 |
| rating.proposed | 脚本由初评＋复核派生 | 不直接等同于联盟已经登记 |
| 实际登记等级 | 当前世界内已确认事实 | 原作 NPC 用对应时期档案；U 在建档/剧情确认后记录 |
| 当前魔力、原生上限、外源能量 | 本轮尚未初始化数值 | 后续战斗脚本单独拥有，不能从 rank 自动生成 |
| 觉醒、关系、事件 | 当前故事分支 | 不因评级或导入人物草稿自动觉醒/恋爱 |

`assessment.basis` 精确绑定建档字段和六轴；任何相关编辑使旧复核失效。`request_id` 是防止误用旧回复的短指纹，不是 AI 身份认证或防恶意修改机制。JSON 与本机槽位属于可编辑草稿，不能作为不可信客户端对正式状态的授权依据。

## 状态与迁移

- `awaiting_axes`：四个计算轴有未知，base/proposed 为空。
- `awaiting_review`：有 base，无已应用复核，proposed 为空。
- `reviewed_proposal`：有经过格式校验的复核，proposed 为拟定登记级，不声明行政登记已完成。
- `canon`：一辉开局原作 F 档案，忽略导入文件对其数值与评定的改写。
- v2 导入：保留旧字段和照片，新能力字段为空、assessment 为空；按已有六维重算初评。v2 未知字段不猜测迁移。
- v3 导入：校验评定与当前依据相符，忽略文件内缓存 rating 和自定义 rank，重算。错误输入不覆盖当前表单。
- 沿用原有三个槽位键便于读取旧草稿；只有用户点击保存才覆盖相应槽，导出统一为 v3。

## 宿主接线要求

识别实际 SillyTavern、Tavern Helper、MVU 和 EJS 版本后，再实现发送、初始化与楼层事务。不从普通页面猜宿主私有 DOM，不假设存在某个全局发送函数。

初始化必须绑定当前聊天与明确消息/分支，支持同一事务重复触发不重复应用；失败应保留草稿且不给出“已入局”。变量更新白名单按字段所有者检查，拒绝通过替换父对象绕过保护。切聊天、编辑、重生成、swipe 和回滚必须读取对应分支，不能复用另一局缓存。

EJS 在本项目只负责读取状态、选择内容与展示；酒馆助手脚本负责确定性校验及结算；AI 提供叙事和结构化提议。未启用或未就绪时显示待接入，不伪造完成状态。
