## 代码因果

1. `scripts/rakudai-state-browser.js:82` 的 capture 入口无超时等待 `waitGlobalInitialized('Mvu')`。开局页 `index.html:11481` 先显示核对提示，随后 await capture。框架没有发布就不会进入写入步骤。
2. `第一卷-世界书整理/开局网页正则替换/index.html:11444`，复制草稿增加 `openingUiRevision`。`enterGame` 在 `:11483` 等待返回后发现序号已改变，会直接退出。复制按钮在等待期间仍可点。
3. 学战草稿文案 `index.html:12557` 与用户截图 2 的“上述资料是草稿，尚未写入游戏状态”一致。模型产出正文不能代替代码提交和回读。
4. `scripts/rakudai-state-browser.js:46` 只允许当前最新助手楼层建档。若等待时已发送草稿并生成后续助手消息，返回原开局页可能再遇到历史楼层保护，不能假定在那里重按就能修复。
5. 终端也可能因状态读取异常或最新楼层只有部分数据而显示等待；该 UI 单独不足以锁定根因。终端展开时每秒重读，不是把最初的空状态永久缓存。

## 补充：不是已确认的“超时”，而是未完成的异步等待

追问后进一步读取了本机酒馆助手 4.12.0 的源码和实际 dist，并提取 dist 中的等待函数，与 SillyTavern 实际 `public/lib/eventemitter.js` 一起做了隔离实验。见 `probe-helper-waits.mjs`、`helper-wait-mechanism-report.json`。

准确链条为：点击建档 → `openingCommitBusy=true`、禁用按钮 → await MVU readiness → 未满足时不进入后面的写入 → finally 尚未执行，busy 也未释放。`index.html:11470` 对 busy 时的重复点击直接 return，不加入提交队列。是这一条操作挂起，不是 JavaScript 主线程整体卡死。

酒馆助手有两种不同等待（本机 `JS-Slash-Runner/src/function/global.ts`）：

1. `:50-61`：宿主尚无 `Mvu`，订阅 `global_Mvu_initialized`，此等待没有超时或失败退出。缺失超过 6.1 秒仍不返回；前一轮真实浏览器在 70.742 秒仍如此。
2. `:40-48`、`:10-15`：宿主已有 `Mvu`，再等首楼或最近十楼出现 stat_data。实际 dist 默认 5000ms，并吞掉超时报错。实验 5011ms 后返回；随后本卡若仍缺当前楼数据，会报明确的缺数据错误。因此单纯 initvar 慢不是本轮人工网络故障长期挂起的原因。

对“队列”的核查：TH 用 Vue v-for 分别挂独立 module iframe，无等待前一个卡脚本完成的串行启动队列。ST 普通事件确实会 await listener，但 `once` 包装器没有返回 listener Promise；本接口使用 once。8 个等待者在约 5011ms 共同结束，并没有排成 8×5 秒。没有发现本卡内建的等待者与 MVU 互相等死。

为了验证区别，还人为添加过一个永久挂起的前置普通事件 listener。该独立实验能堵住旧等待者，但此时**宿主已有 Mvu，旧 iframe 没有，新调用可以成功**。这是外部监听器故障的识别特征，未在玩家或本卡正常运行中观测到，不能认定它是玩家原因。

继续核查固定 MVU `61010dab...`：接口发布在聊天级 initvar、变量事件队列之前。发布前仍有模块及子模块加载、同源 `/version` 请求、唯一实例选择、面板/按钮初始化。`/version` 没有应用层请求超时；唯一实例未获资格也不会发布。bundle 还静态导入 testingcf.jsdelivr.net 的 ESM 子模块，所以主 bundle HTTP 200 不证明已执行到发布接口。以上为代码可达的前置失败点；本轮真实酒馆只实测了 bundle 请求失败这一触发条件，未把其余假设当作玩家故障。

所以已确定的程序缺陷是：**依赖发布失败或停滞，没有传递成建档失败；前端无限等待并保持 busy。** 玩家设备为何没能完成发布，还缺首次错误/请求状态，不能从三张截图唯一反推出 CDN、脚本异常或插件冲突。原先“复制草稿使提交失效”是后续独立路径，不是最初卡住的原因。

## 对玩家反馈的判断与下一次取证

最符合现有证据的链条是：MVU 未就绪 → 建档停住 → 复制并发送仍属草稿的文本 → 故事生成，但系统没有建档。用户补充“应该是等了也没用”，使单纯短暂延迟的解释更弱。不过是否下载失败、脚本未启用或执行异常，仍需玩家侧确认；也未确认玩家是否在等待中点了复制。

下一次复现只需收集三个点：MVU 脚本是否启用及首条网络/控制台错误；卡住后是否点击复制草稿；首楼与最新助手楼层的 `stat_data.系统`。不需要提供 API 密钥或整份设置。

临时操作建议：先等到页面明确显示“建档成功并已回读”，再复制正式第一幕请求；“复制草稿”不完成建档。若已产生后续助手楼层，应保留人物草稿，在新聊天验证依赖就绪后重新建档，避免覆盖旧分支。
