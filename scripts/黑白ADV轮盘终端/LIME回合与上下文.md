# LIME 剧情附属通讯与上下文 · v1.3.28

LIME 是当前剧情楼层附带的通讯界面。明确发送会触发一次酒馆助手辅助生成，让指定人物依据本局情境回信；玩家发信和实际回信共同保存为该楼层的附件，不新增酒馆用户／助手楼层，也不推进主剧情回合。版本与安装文件仍为 v1.3.28。

## 一次发送的边界

发送前确认联系人已交换联系方式、当前助手回复及 MVU 已就绪，并冻结角色、聊天、楼层、活动 swipe、页数和该楼层的剧情时间。读取世界书中的收信者人物词条与当前 MVU 关系资料后，用酒馆助手公开生成接口发起一次辅助请求。辅助请求使用当前连接、预设和宿主实际纳入的本局上下文，不另选一套私聊模型，也不能恢复已被宿主裁掉的历史。

辅助请求只扮演收信者的通讯回复，不续写主剧情、补造玩家行动、输出 MVU 更新或改变剧情时间。没有实际回信时不虚构对话；不会自动循环请求、模拟后台聊天或补造在线、送达、已读状态。打开 LIME、搜索、读记录和准备草稿都不调用模型。

生成与保存前后都核对冻结的来源。来源改变时不向另一聊天或回复页补写结果；等待中的重复点击不再次派发。只有通讯保存接口确认后清空该联系人的草稿；失败保留原文，提示先核对记录再重试。

## 人物性格与关系

人物性格来自本局绑定世界书中可明确对应收信者的人物词条。终端将该词条作为本次辅助请求的角色依据，而不是仅靠称呼触发世界书后假定它已经进入上下文。找不到可核实的人物词条时拒绝发送并保留草稿，不能用一套泛化人格代替。

同次请求还读取当前楼层 MVU 中该人物的关系、态度印象、好感、支援及已知资料。关系决定熟悉程度、称呼与互动边界；数值只是当前关系的证据，不能自动抹掉人物性格、原有立场、保密范围或承诺。没有已确认恋爱关系时，不因高好感直接写成恋人。

辅助通讯本身不直接修改 `stat_data`，也不自动增加好感、支援或奖励。下一次主剧情可依据实际联络产生的新证据结算关系变化；不能因为旧通讯再次被纳入上下文就重复计分。这是剧情与模型提示约束，不是新增一套自动计分器。

## 时间与回复页归属

列表、时间分隔与气泡时间读取该记录所属楼层的 MVU `stat_data.场景.时间`。附属发送保存发信时冻结的时间，后续剧情前进不会重新计算旧通讯；主剧情主动来信读取其已完成助手楼层的 MVU 时间。缺失时显示「时间未记录」，不取电脑时钟、其他楼层或最新共享状态补值。

同一回复页执行续写时，已保存的正文来信在 `narrative` 快照中保留各自时间；只有位置、对象与正文仍匹配的旧来信沿用快照时间，新来信取续写完成后的该页 MVU 时间。每次附属通讯还记录发信前已有几条正文来信的 `narrativeCount`，把气泡插在当时的位置：旧来信 → 附属发信与回信 → 后来续写的新来信。同页续写流式期间，已验证的旧来信和附件仍可显示，新流式来信等待完成，不把旧通讯整体挪到新时间或新来信之后。

附属通讯放在当前回复页的 `data.rk_lime`，与 MVU 的 `data.stat_data` 并列，不新增正式 MVU 聊天字段。以下是虚构结构示例：

```json
{
  "version": 1,
  "owner": { "messageId": 12, "swipeId": 0 },
  "narrative": [
    { "contact": "风祭凛奈", "text": "集合地点已确认。", "time": "2013-05-15 16:15" }
  ],
  "exchanges": [
    {
      "id": "example-exchange",
      "contact": "风祭凛奈",
      "time": "2013-05-15 16:20",
      "narrativeCount": 1,
      "player": "现在方便吗？",
      "reply": ["方便，怎么了？"]
    }
  ]
}
```

`owner` 必须与当前读取的楼层 ID 和活动 swipe 一致。MVU 继承上一楼层变量时即使复制了附件，所有者不符也不会当作新楼层通讯显示。读取只使用当前分支的活动回复页，不拼合未选择的 swipe、未来楼层或另一聊天的缓存；历史附件按各自所有者读取，新增通讯只写当前剧情来源。

删除前面的楼层或回复页可能改变剩余对象的编号。只有终端见证了删除事件、能够核对原对象的连续性时，才为确认保留下来的附件重绑 `owner`；已识别的继承副本先隔离，不能因编号挪动而被重新认作原件。没有删除见证或无法核对来源时，不凭姓名、正文相似或新的编号猜测归属。

保存时仅追加已验证的通讯，保留同回复页其他变量，不将生成文本当作 HTML 或可执行代码。单条玩家消息限 4000 字符；异常形状、超限文本和其他角色冒名回信不部分接收。

## 主剧情也可以主动来信

正常主生成可以在正文中输出明确、闭合的 `<LIME>` JSON，使人物主动发来短信，无需玩家先从手机发送。示例是格式说明，不代表本局已经发生：

```text
<LIME>
{"对象":"夏洛特·科黛","消息":[{"发言人":"夏洛特·科黛","内容":"集合地点已经确认。"}]}
</LIME>
```

主剧情助手楼层只接受对象本人的发言，不能补造玩家消息；普通旁白、普通台词、残缺 JSON 与未完成的流式输出不会变成来信。对象、消息和每项的发言人／内容都验证形状。该来信沿正常主剧情和 MVU 保存链处理，时间从该楼层完成后的 MVU 读取。

## 进入下一次主剧情上下文

当前分支的有效附属通讯在下一次正常主生成前以有记录数量与文本长度边界的提示注入，让主剧情能够读取此前真实保存的联络。注入内容按当前楼层与活动回复页重读，换聊天、切 swipe、删除或回退后移除不再属于当前分支的记录。

正式主生成开始前，另外选择当前分支最近有通讯、并且当前仍已建立联系方式的最多 3 名联系人，显式读取其主世界书人物原文和当前 MVU 关系资料，并附带本局主角模式。主剧情收到手机来信时因此也有明确的人物性格与认知依据；其他人物继续使用原来的世界书触发方式，不全量载入通讯录或给所有人物套用同一性格。准备过程中来源变化时，旧读取结果不能进入新分支请求。

这一步在原生 START 中被等待，最长 5 秒，期间不能再插入手机辅助生成。缺失、停用或超出本轮 64000 字符原文预算的联系人档案会跳过；读取超时继续普通主剧情，不用旧分支材料补齐。临时人物提示在主生成结束、中止、切分支或终端销毁时撤销，不残留到开局建议或辅助通讯请求。

注入只补充附属通讯，不再重复塞入全部聊天历史，不承诺突破宿主上下文窗口、预设裁剪或世界书配置。主剧情中的显式 `<LIME>` 来信本来就在原生正文中，不能因此补造第二次发信或重复结算关系。

## 草稿与界面

「战术联络」「约练习」「问候」只准备可修改的草稿。Enter 换行，Ctrl／⌘ + Enter 或发送按钮才提交；输入法组字期间不提交，空消息不能发送。

每个联系人有独立的临时草稿与滚动位置，同一聊天普通刷新保留输入。切聊天、切 swipe、删除楼层或选择新首条消息时清理分支 UI；草稿只存在当前终端实例内存，重载页面不持久保存。辅助通讯不写入或覆盖酒馆主输入框。

聊天列表和气泡跟随终端黑白主题，头像使用统一素材清单，未知人物或加载失败保留首字回退。联络资料可折叠，返回先回名册。发送按钮显示「发送消息」，说明为「通讯附于当前剧情」，不再展示酒馆回合编号。

## 适配与验收边界

接入依据为本地核实的 Tavern Helper 4.8.19 公开生成、消息读取、变量写入与提示注入契约；运行时逐项检查所需能力。接口缺失、MVU 等待中、主生成忙碌、来源改变、人物未通联或缺少性格词条时保持诊断并保留草稿，不调用私有酒馆函数或模拟主发送按钮。

保存接口的成功返回目前证明变量已更新并进入宿主保存队列，不能据此声称磁盘已经落盘。真实酒馆的辅助生成、回信保存、页面重载恢复及下一次主生成读取完整链路仍需实际验收。

支持检查见 [lime-chat-test.mjs](lime-chat-test.mjs)、[lime-host-test.mjs](lime-host-test.mjs)、[lime-ui-test.mjs](lime-ui-test.mjs)、[shell-test.mjs](shell-test.mjs) 与 [宿主送信验证记录](验证记录/LIME宿主送信.json)。验收应观察：一次发送得到合法回信，主聊天楼层数不变；同页续写的旧来信保留旧时间，附属气泡顺序不变；有见证的删楼或删回复页只重绑原件，继承副本不复活；人物词条与当前关系进入辅助及正式主剧情请求；好感未被辅助请求直接改变；切分支不串消息；下一次主剧情读取已保存通讯。

本地预览入口为 `preview.html?sample=lime&view=lime`，由 [preview.mjs](preview.mjs) 构建。预置人物回信明确标注为虚构样本；按发送仅向当前演示剧情追加 `reply: []` 的本地记录，楼层数保持 2 → 2，不调用模型或生成 NPC 回答。真实导入只替换同名 [小手机 v1.3.28](../../世界书规则/MVU/落第骑士-小手机-v1.3.28.json)，步骤见 [QUICKSTART](QUICKSTART.md)。
